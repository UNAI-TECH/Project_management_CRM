This document analyzes the 16 Word-based project management templates currently used by the CTO office at UNAI Tech (Project Charter through Maintenance Plan, plus the Master Record) and translates the entire paper-based workflow into a single scalable, cross-platform application — built on Expo (mobile) wrapped by Electron (Windows desktop .exe) — with authentication federated through a shared Onboarding Platform (HR CRM assigns the roles, the platform proves identity to every CRM), hierarchical task assignment, and CTO-controlled document generation that exports back into the exact same template formats.

1. Executive Summary
UNAI PM CRM replaces the current Word-document-driven project lifecycle (16 templates filled and circulated manually per project) with a single application where every document is a structured, database-backed record. Employees no longer fill Word files — they fill screens; the application generates the identical Word/PDF output on demand, whenever it's needed for a client, auditor, or archive.
Three ideas anchor the whole design:
Identity comes from a shared Onboarding Platform, not from this app or even from HR CRM directly. Every CRM UNAI Tech runs — HR CRM, Finance CRM, PM CRM, and any future one — is a client of that one platform. HR CRM decides who exists and what role they hold; the Onboarding Platform is the only place a password ever lives.
The CTO is the single point of structural control. Only the CTO can create projects, create/delete document records, and create/delete users' project access. Everyone else can only update the records they've been given access to — they cannot create or delete.
Every action is a row in an audit trail. Task assignment, task submission, task verification, and document edits are all logged, which is what lets the CTO dashboard offer full combinational filtering and one-click exports — that's the paperless replacement for signature pages and status columns.

3. Roles & Access Control Model
3.1 Role hierarchy
Roles are not stored or invented in PM CRM — they are read from the Onboarding Platform at login (see Section 4). HR CRM is who decides the role; the Onboarding Platform is where that decision is recorded and handed to PM CRM as a signed claim. PM CRM then scopes that role to a specific project via Project Membership, which only the CTO can create.

4. Onboarding Platform & Federated Authentication Architecture
There is no login inside PM CRM, and there's no separate login owned by HR CRM either. Both — and Finance CRM, and any CRM UNAI Tech builds after this — sit on top of one shared Onboarding Platform, built on Supabase Auth. It is the only place a work password ever exists. HR CRM's job is deciding who exists and what role they hold in which CRM; the Onboarding Platform's job is proving identity and handing each CRM a signed, role-scoped token. This is the same shape as “Sign in with Google” across Google's own products — one identity provider, many relying applications.
4.1 The three pieces
Onboarding Platform — a dedicated Supabase project (auth.users + a small onboarding schema) plus a lightweight backend. Hosted at onboarding.unaitech.com. This is the identity provider for the whole company, not a PM CRM component.
HR CRM — where HR staff onboard a new hire and assign CRM roles. HR CRM never stores or sees a password; every create/role-change action it performs is written through to the Onboarding Platform over a server-to-server Admin API.
Consumer CRMs — HR CRM's own front end, Finance CRM, and PM CRM (web subdomain + Electron desktop) are all “clients” of the Onboarding Platform. None of them authenticate anyone directly — they only accept a token the Onboarding Platform already signed.

4.2 Onboarding backend flow — how a person enters the system
HR staff creates the employee record in HR CRM: name, department, designation, and a unique work email (e.g. name@unaitech.com).
HR CRM calls the Onboarding Platform's Admin API — a server-to-server call using a service-role key that is never exposed to any browser — to create a Supabase Auth user for that work email.
Instead of HR typing a password on someone else's behalf, the Admin API triggers Supabase's invite-by-email flow: the new employee receives a “set your password” link on their work Gmail and chooses their own password. HR CRM, and every other CRM, remains permanently password-blind.
HR CRM then writes one row per CRM into the Onboarding Platform's onboarding_role_grants table via the same Admin API — e.g. “PM CRM: Team Lead,” “Finance CRM: Viewer.” This is literally the “assigning roles to onboarding users” step you described.
Any later change in HR CRM — a promotion, a project move, a resignation — fires the same Admin API call and updates onboarding_role_grants / is_active immediately. Because every CRM session is short-lived (Section 4.5), that change reaches every CRM within one token refresh, not on some separate nightly sync.

4.3 Logging into a web-hosted CRM (subdomain SSO)
Applies to HR CRM, Finance CRM, and the PM CRM web build, each on its own subdomain.
Employee opens any CRM subdomain (e.g. pm.unaitech.com) without an active session and is redirected to the single shared login page at onboarding.unaitech.com.
They sign in once with their work email + password, checked by Supabase Auth inside the Onboarding Platform — nowhere else.
The Onboarding Platform checks onboarding_role_grants for that specific CRM. No active grant → the flow stops here with “No access to PM CRM — contact HR,” and PM CRM is never reached.
If a grant exists, the Onboarding Platform issues a one-time signed authorization code and redirects the browser to https://pm.unaitech.com/auth/callback?code=...&state=....
PM CRM's own backend exchanges that code server-side for a PM-CRM-scoped session JWT. This exchange happens machine-to-machine, so the code is useless to anyone who intercepts it in the browser.
PM CRM sets its own session from that JWT — the employee is in. Because step 2 also set a shared session cookie on the root unaitech.com domain, moving to another CRM subdomain repeats steps 3–6 automatically, with no password re-entry. That's the SSO part.

4.4 Logging into the PM CRM desktop app (.exe)
A desktop app can't rely on shared browser cookies, and it must never show its own login form — that would mean the app's own code sees the password. So the desktop flow hands the entire login step to the machine's real browser and gets back only a one-time code, using the OAuth2 Authorization Code + PKCE pattern that's the standard approach for native apps (the same shape Slack, VS Code, and 1Password's desktop apps use).
The PM CRM desktop app opens the system's default browser to onboarding.unaitech.com/login, tagged with client=pm-crm-desktop, a redirect target of the custom URI unaipmcrm://auth-callback, and a PKCE challenge generated locally by the app itself.
If the employee already has a live onboarding.unaitech.com session in that browser, this is invisible — otherwise they log in exactly as in Section 4.3.
The Onboarding Platform checks the PM CRM role grant exactly as before. Instead of redirecting to a subdomain, it redirects the browser to unaipmcrm://auth-callback?code=....
The operating system hands that link to the PM CRM desktop app, registered as the handler for unaipmcrm:// at install time — the running app receives the code directly, with no copy-pasting.
The desktop app exchanges the code, together with the PKCE secret only it knows, directly with the Onboarding Platform over HTTPS — receiving a short-lived session JWT and a longer-lived refresh token.
The refresh token is stored encrypted in the OS credential store (Windows Credential Manager, via a library like keytar). Next launch, the app renews its session silently in the background — no browser hop needed — until that refresh token itself expires or HR revokes access.

4.5 Session control & revocation
Every token issued — web or desktop — is recorded in a central auth_sessions table on the Onboarding Platform, so one action (“revoke all sessions for this employee”) logs them out of every CRM, on every device, at once.
Because session JWTs are deliberately short-lived (e.g. 15 minutes), a revocation or a role change in HR CRM takes effect everywhere within one refresh cycle — there's no CRM quietly running on stale access.
This keeps the earlier CRUD boundary intact: HR CRM controls who exists and what CRM roles they hold; the CTO still controls everything that happens once someone's inside PM CRM specifically (Section 3.2). The two systems don't compete for authority — identity vs. in-app control are cleanly separate concerns.

4.6 Edge cases
Not in the Onboarding Platform at all → can't even reach a CRM login screen; rejected at onboarding.unaitech.com itself.
Has an onboarding account but no PM CRM role grant → SSO login completes fine, but PM CRM shows “No PM CRM access — contact HR” and loads nothing.
Has a PM CRM grant but isn't yet a Project Member anywhere → same as before: dashboard shows “No project assigned — contact your CTO.” This is the state a brand-new intern lands in until the CTO assigns them.
Onboarding Platform temporarily unreachable → an already-issued, unexpired session JWT keeps working locally until its short TTL lapses; no new logins and no token refreshes can complete until the platform is back — by design, since this is now the single point every CRM depends on (see Section 13).

5. System Architecture
5.1 Application layer — one codebase, two shells
A single Expo (React Native + TypeScript) codebase produces:
A mobile app (iOS/Android via EAS Build) for TLs and employees working on-site (e.g. My Vidyon installation visits), including offline task viewing/submission with a local sync queue.
A Windows desktop .exe by exporting the Expo project for web and packaging that build inside Electron — this is what the CTO and PMs use for the heavier dashboard/filtering/export work at a desk.
Shared UI kit (NativeWind/Tailwind-for-RN or Tamagui) so screens, components and business logic are written once and simply rendered natively on mobile and via the Electron webview on desktop — matches the frontend-first, single-source pattern you've used on SamruddiSave and UNAI Flow.

6. Core Data Model
6.1 Two database scopes — don't mix these up
With the Onboarding Platform in the picture, there are now two clearly separate databases, owned by two different teams:
Onboarding Platform database (shared, owned by HR/IT, outside PM CRM entirely): auth.users (Supabase Auth), onboarding_role_grants, oauth_clients, auth_sessions. PM CRM never writes to this database — it only ever receives a signed JWT derived from it.
PM CRM's own database (a separate Supabase project, owned by the CTO office): everything in the table below. employees_cache is the one table that bridges the two — it's populated purely from the claims inside each login JWT, not by a separate sync job or direct database link.

Every PM CRM table includes created_at, updated_at, and is written to audit_log on every INSERT/UPDATE/DELETE via a Postgres trigger — that trigger is what gives the CTO dashboard its full history without any extra work from users.

7. Document Engine — Forms In, Exact Templates Out
7.1 How a template becomes a form
Each of the 16 templates is converted once into a JSON form schema that mirrors its exact sections (e.g. the Project Charter schema has purpose, objectives[], scope_in[], scope_out[], milestones[table], stakeholders[table], risks[], budget, approval). The schema — not the app's code — defines the form, so adding a 17th template later (Section 11, Scalability) never requires a new app release.
7.2 Filling and versioning
Whoever the CTO has granted access to a document (per Section 3.2) fills their sections directly on screen; the record saves as project_documents.content.
Every save creates a document_versions row — nobody can silently overwrite history, and the CTO can diff or roll back to any prior version.
A document's status (draft → in_review → approved) is itself a field the CTO controls, standing in for the old “Approval” signature block.
7.3 Exporting — the paperless part that still produces paper when you need it
At any point, any authorized viewer can hit “Download” and the Document Export Service renders the current JSONB content back into a .docx (and optionally PDF) laid out identically to the templates you uploaded — same headers, same tables, same Document Control block, now auto-filled instead of blank. Downloads can be filtered and bulk-exported (e.g. “every approved Test Case document across every active project this quarter”) as a ZIP, which is the direct replacement for digging through a shared drive of Word files.

10. Security & Enforcement
No local password store — not in PM CRM, and not in HR CRM either. Only the Onboarding Platform ever holds one, which removes an entire class of credential-leak risk from every other system UNAI Tech runs.
Every table has Row-Level Security policies keyed off the session JWT's employee_id, pm_crm_role, and project_ids — enforced at the database, not just hidden in the UI.
INSERT and DELETE policies are CTO-only (or CTO-delegated for task creation, per Section 3.2) at the database level, so even a compromised or buggy client can't create/delete records it shouldn't.
Every mutation is captured by trigger into audit_log — this is the mechanism that lets you say “every process is fully controlled by the CTO” and actually mean it, since nothing can happen invisibly.
Access can be pulled company-wide from one place: revoking an employee's Onboarding Platform sessions (Section 4.5) logs them out of PM CRM, HR CRM, and Finance CRM simultaneously — offboarding is one action, not one per CRM.

11. Scalability & Upgrade Path
organization_id is included on every table from day one, even with a single tenant today — so the same platform can later be offered to other teams or even externally (in the spirit of My Vidyon / UNAI Flow) without a schema rewrite.
Document templates are versioned JSON schemas, not hardcoded forms — the CTO office can add a 17th template type through an admin screen, no app release required.
Backend is split into independently deployable services (Auth Bridge, Task Engine, Document Engine, Notification Engine) behind a single API gateway, so any one service can scale or be rebuilt without touching the others.
Mobile is offline-first (local cache + sync queue) for field work like on-site installs, syncing automatically once connectivity returns.
